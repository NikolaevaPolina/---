# Платформа данных службы технической поддержки

Автономный макет платформы сбора, хранения и обработки обращений пользователей корпоративных ИТ-сервисов. Он показывает полный путь данных: от программного источника до аналитических витрин, рекомендации категории и панели. Макет использует синтетические заявки и не подключается к рабочей системе IntraService.

## Что реализовано

- имитатор Service Desk API с постраничной выдачей и отбором изменённых заявок;
- полная и выборочная загрузка, история версий в исходном слое;
- хранилище `Bronze → Silver → Gold` в PostgreSQL: типизация, очистка, обогащение и три аналитические витрины;
- шесть обязательных проверок качества, журнал запусков и отметка успешной загрузки;
- два метода классификации темы обращения: наивный байес и центроидный метод;
- рекомендации категории для открытых обращений без автоматического изменения исходной категории;
- панель с графиками потока, сроков, нагрузки, качеством данных и результатами классификации;
- воспроизводимый запуск служб через Docker Compose и учёт версий проекта в Git.

## Конвейер

```text
Имитатор Service Desk API
  → Bronze: версии сообщений и сведения о загрузке
  → Silver: актуальные типизированные обращения
  → Gold: витрины потока, сроков и нагрузки
  → проверки качества данных
  → классификация: обучение при полном запуске, применение модели при выборочном
  → аналитическая панель и рекомендации категории
```

Схема и описание этапов приведены в [тексте ВКР](docs/thesis_text.md). В конвейере используются Python, FastAPI, SQLite, PostgreSQL, Streamlit и Plotly. Исходный источник и аналитическое хранилище разделены. Все компоненты запускаются в контейнерах.

## Быстрый запуск

Нужен установленный и работающий Docker Desktop. В папке проекта выполните:

```bash
docker compose build mock-api etl dashboard
docker compose up -d db mock-api dashboard
docker compose run --rm etl python -m etl.cli full
```

После полной загрузки откройте [документацию имитатора](http://localhost:8000/docs) и [аналитическую панель](http://localhost:8501). На Windows те же действия выполняет `scripts/start.ps1`.

## Выборочное обновление

Создайте 100 новых обращений и измените 20 существующих:

```bash
curl -X POST "http://localhost:8000/admin/advance?new_count=100&update_count=20"
```

```bash
docker compose run --rm etl python -m etl.cli incremental
```

На Windows можно выполнить `scripts/incremental-demo.ps1`. Обновите страницу панели: в разделе «Качество и запуски» появятся число полученных изменений и время этапов. Результат классификации для изменённых открытых заявок появится в разделе «Классификация».

## Результаты испытания

Итоговый опыт выполнен на трёх уровнях истории: 30 300, 35 000 и 40 000 заявок. На каждом уровне проведено по три повтора с пакетом из 100 новых и 20 изменённых заявок. Медианное время полного конвейера составило 10,418–15,457 с, выборочного — 0,422–0,499 с. Отношение времени составило 24,69–30,98. Оно относится ко всему пути обработки, включая переобучение при полном запуске, и не означает ускорение только построения витрин. Данные измерений: [таблица](artifacts/final_model/benchmark_stable_summary.csv), [подробные замеры](artifacts/final_model/benchmark_stable_details.csv), [график](artifacts/final_model/benchmark_stable.svg).

На обычной проверочной выборке оба классификатора показали 100 % точности из-за повторения шаблонов тем. При проверке на ранее не встречавшихся формулировках центроидный метод достиг 20,28 % точности и меры F1 0,0808. Это недостаточно для автоматического назначения категории. Рекомендации в панели служат демонстрацией обработки подготовленных данных.

Для повторения измерений на **чистом стенде** после первоначальной полной загрузки выполните:

```bash
docker compose run --rm etl python -m etl.benchmark_stable --targets 30300 35000 40000 --repeats 3 --batch-size 100 --output-dir /artifacts/final_model
```

Если в источнике уже больше заявок, сценарий не уменьшит их число и исходные уровни опыта изменятся.

## Границы макета

Программный интерфейс имитатора соответствует смыслу сущностей Service Desk, но его совместимость с закрытым интерфейсом IntraService не заявляется. Реальная интеграция требует отдельного изучения доступного способа выгрузки и согласования прав. Поиск похожих закрытых обращений и подготовка проекта ответа специалисту остаются направлениями развития. Испытания проведены на синтетических данных и одном компьютере; промышленная масштабируемость и качество классификации на реальных обращениях не оценивались.
