# Сценарий демонстрации на защите

## Подготовка заранее

Убедиться, что Docker Desktop запущен. Создать `.env` по образцу `.env.example` и задать пароль базы. В папке проекта выполнить `docker compose up -d db mock-api dashboard`, затем `docker compose run --rm etl python -m etl.cli full` и `docker compose --profile operator up -d --build operator`. Проверить <http://localhost:8000/docs>, <http://localhost:8501> и <http://localhost:8502>. Сохранить презентацию и снимки экранов для показа при задержке запуска.

## Демонстрация за 4–5 минут

1. Показать схему единого конвейера: имитатор API → исходный слой Bronze → очищенный Silver → витрины Gold → проверки качества → классификация → панель.
2. Открыть `/stats` в документации имитатора. Пояснить, что источник синтетический и не подключён к IntraService.
3. Открыть панель. Показать графики потока обращений, сроков и нагрузки, затем раздел «Качество и запуски» с шестью проверками.
4. В разделе «Классификация» показать сравнение двух методов и рекомендации для открытых обращений. Сказать, что на новых шаблонах центроидный метод дал 20,28 % точности и мера F1 составила 0,0808. Поэтому категория не назначается автоматически.
5. Открыть экран специалиста. Выбрать открытую заявку, показать похожие закрытые обращения и редактируемую рекомендацию. Нажать «согласовать» или «отклонить»; решение сохранится, но ответ не уйдёт заявителю. Уточнить, что сходство текста рассчитывается по простому правилу и качество на реальных заявках не измерено.
6. Выполнить в PowerShell `./scripts/incremental-demo.ps1`. Сценарий создаст 100 новых заявок и изменит 20 существующих, затем запустит выборочный конвейер. Показать технический журнал командой `docker compose logs --tail=30 etl`: этап, число записей и длительность без пароля или текста заявок.
7. Обновить данные в панели. Показать новое число обращений, успешный запуск и число полученных изменений. Затем показать [график испытания](../artifacts/final_model/benchmark_stable.svg): на уровнях 40 400–50 000 заявок полный конвейер занял 16,459–22,081 с, выборочный — 0,529–0,566 с.

## Важные пояснения комиссии

- **Почему источник не IntraService?** Доступ к корпоративной системе и её данным не требовался для автономного макета. Интерфейс воспроизводит смысл сущностей Service Desk, но совместимость с закрытым API IntraService не проверена.
- **Где инженерия данных?** В постраничном извлечении, выборочной загрузке, истории версий, типизации, обогащении, контроле качества, витринах, сохранении состояния и оценке времени конвейера.
- **Почему три слоя?** Bronze сохраняет значения и версии полученных сообщений, Silver — одну актуальную типизированную запись на обращение, Gold — рассчитанные показатели для панели и рекомендации категории.
- **Что означает «распределённая»?** Компоненты работают как отдельные сетевые службы в контейнерах на одном компьютере. Отказоустойчивость кластера этим не подтверждается.
- **Есть ли ИИ?** Реализовано сравнение двух методов классификации темы. Качество на новых формулировках низкое. Дополнительный экран ищет похожие заявки по совпадению слов и предлагает текст прежнего решения для редактирования; это не проверенная генеративная модель.
- **Где логирование и как защищено подключение?** Журнал контейнера показывает этапы и время. Запросы к базе собраны в отдельных классах. Пароль берётся из локального `.env`; в Git он не включается, а экран не показывает диагностическую строку подключения.
- **В чём ограничение результата испытания?** Измерения относятся к синтетическому набору и одному компьютеру. Отношение времени 31,11–40,52 характеризует весь конвейер, включая переобучение модели при полном запуске. Само построение витрин не показало устойчивого выигрыша выборочного режима.
